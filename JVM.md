| 1 | JVM | The Java Virtual Machine is an abstract computing machine responsible for executing Java bytecode. It acts as a software layer between Java applications and the operating system. The JVM provides memory management, garbage collection, thread scheduling, class loading, security verification, and runtime optimization. Most developers think of JVM merely as "the thing that runs Java", but its actual role is to create a controlled execution environment independent of hardware and operating systems. | Before Java, software had to be compiled separately for different operating systems and processor architectures. | 2 | Heap | Heap is the shared runtime memory area where objects and arrays are allocated. All application threads can access heap memory. Whenever a developer creates an object using the new keyword, memory is generally allocated from the heap. Heap is not merely "memory"; it is specifically designed for dynamic object allocation and lifecycle management. | Objects often need to outlive method execution. If objects were stored only inside method stacks, they would disappear immediately after method completion. | Heap means total application memory. Heap contains everything used by Java. Heap and RAM are identical concepts. | Provide centralized storage for objects whose lifetime is not tied to a specific method invocation. | Spring singleton beans, entity objects, DTOs, collections, caches, and configuration objects all reside in heap memory. | Difference between Heap, Stack, and Metaspace. Explain memory leaks in heap. Explain heap dump analysis. | Eden Space, Survivor Space, Old Generation, GC |
| 3 | Stack | Stack is a thread-private memory area that stores execution context. Every thread gets its own stack. The stack contains method frames, local variables, method parameters, return addresses, and intermediate computation results. Conceptually, the stack represents the execution history of a thread. | The CPU must know which method is currently executing and where control should return after method completion. Stack memory provides an efficient Last-In-First-Out (LIFO) structure for method execution tracking. | Objects are stored in stack memory. Stack is shared among threads. Stack is only used for primitive variables. | Track execution flow and method invocation hierarchy efficiently. | Controller → Service → Repository call chain creates multiple stack frames during request processing. | What causes StackOverflowError? How does recursion impact stack memory? Why does each thread have its own stack? | Thread Stack, Method Frame, Heap |
| 4 | Eden Space | Eden Space is the nursery region of the JVM heap where newly created objects are initially allocated. The name comes from the Garden of Eden because it is the place where object life begins. JVM designers observed that most objects die shortly after creation, so a specialized area was created to optimize their management. | Research showed that most objects have extremely short lifetimes. Temporary Strings, DTOs, loop variables, and intermediate objects often become unreachable within milliseconds. | Objects remain in Eden throughout their lifetime. Eden is simply another memory partition without a special purpose. | Optimize allocation and garbage collection for short-lived objects. | Request DTOs created during REST API calls often die before the request finishes. | Explain Minor GC. What happens when Eden becomes full? Why is object allocation usually extremely fast? | Survivor Space, Young Generation, Generational Hypothesis |
| 5 | Survivor Space | Survivor Space acts as a probation zone for objects that survive garbage collection in Eden. Instead of immediately promoting surviving objects to long-term storage, JVM keeps them under observation. Objects move between Survivor regions while their age is tracked. | Surviving one garbage collection does not necessarily indicate a long-lived object. Many objects survive briefly but still die soon afterward. | Objects move directly from Eden to Old Generation. Survivor spaces permanently store objects. | Reduce unnecessary promotions to Old Generation and improve garbage collection efficiency. | Session-related objects that survive a few requests before disappearing. | Explain object aging. What is Tenuring Threshold? Why are there typically two Survivor regions? | Eden Space, Old Generation, Minor GC |
| 6 | Old Generation | Old Generation is the area where objects are stored after surviving multiple garbage collection cycles. It contains objects considered long-lived by the JVM. These objects typically remain reachable for extended periods. | Long-lived objects behave differently from short-lived objects. Managing both categories using identical algorithms would reduce garbage collection efficiency. | Old Generation contains old business data. Objects are manually moved into Old Generation. | Separate long-lived objects from temporary objects to improve memory management. | Spring singleton beans, application caches, configuration objects, connection pools. | Explain Full GC. What causes Old Generation exhaustion? How does promotion failure occur? | Survivor Space, Major GC, Full GC |
| 7 | Metaspace | Metaspace is the memory area used to store class metadata. It contains information about loaded classes, methods, fields, annotations, and runtime type structures. Unlike Heap, Metaspace primarily stores class definitions rather than application objects. | JVM must understand class structure before executing code. Runtime reflection, dependency injection, annotations, and proxy generation all depend on metadata availability. | Metaspace stores application objects. Metaspace and Heap are identical. | Store runtime class information efficiently. | Large Spring Boot applications may load thousands of classes and generated proxies into Metaspace. | Difference between PermGen and Metaspace. What causes Metaspace OutOfMemoryError? | ClassLoader, Reflection, Bytecode |
| 8 | ClassLoader | ClassLoader is a subsystem responsible for loading class definitions into memory. It converts class files into runtime structures understood by the JVM. Class loading occurs dynamically as needed rather than loading every class during startup. | Loading every class at startup would dramatically increase startup time and memory consumption. Lazy loading improves efficiency. | All classes load when the application starts. There is only one ClassLoader. | Dynamically load classes while supporting modularity, isolation, and extensibility. | Spring Boot DevTools, application servers, plugin architectures, and OSGi frameworks depend heavily on ClassLoader isolation. | Explain parent delegation model. | 9 | Bytecode | Bytecode is the intermediate platform-independent instruction set produced by the Java compiler. JVM executes bytecode rather than Java source code. Bytecode acts as a portable representation of program logic. | A platform-neutral representation allows applications to run on different operating systems without recompilation. | JVM executes Java source code directly. Bytecode is machine code. | Provide portability and enable runtime optimization. | The Employee.class file generated by javac contains bytecode instructions. | Explain the compilation process from source code to execution. How can bytecode be inspected? | JIT Compiler, ClassLoader, JVM |
| 10 | JIT Compiler | The Just-In-Time Compiler converts frequently executed bytecode into native machine code during runtime. Instead of repeatedly interpreting bytecode, JVM identifies hot code paths and compiles them into highly optimized processor instructions. | Pure interpretation is slower because each instruction must be repeatedly translated. Runtime compilation significantly improves performance. | Java is interpreted only. JIT simply caches results. Java is always slower than native languages. | Deliver near-native execution speed while preserving portability. | Frequently executed methods in high-traffic Spring Boot APIs become optimized native machine code after warmup. | Explain JVM warmup. What are C1 and C2 compilers? Why are benchmarks often misleading without warmup? | Bytecode, Code Cache, Escape Analysis |
| 11 | Garbage Collection (GC) | Garbage Collection is the JVM mechanism responsible for automatically reclaiming memory occupied by unreachable objects. Contrary to popular belief, GC does not determine whether an object is useful; it determines whether an object can still be reached from active parts of the application. If no path exists between a GC Root and an object, that object becomes eligible for collection. | Manual memory management is error-prone. Languages like C and C++ require developers to explicitly release memory, often leading to memory leaks, dangling pointers, and crashes. Java introduced automatic memory management to eliminate these problems. | GC removes useless objects. Calling `obj = null` immediately frees memory. GC runs continuously. | Automatically manage object lifecycles and reclaim unused memory without developer intervention. | Millions of temporary request objects created in a Spring Boot API are automatically removed after requests complete. | Explain Mark-and-Sweep, Mark-and-Compact, Generational GC, Stop-The-World pauses, and concurrent collectors. | GC Roots, Reachability Analysis, Heap |
| 12 | GC Root | GC Roots are the starting points used by the JVM to determine whether objects are reachable. Garbage collectors begin traversal from these roots and follow references through the object graph. Any object reachable from a GC Root is considered alive. | JVM needs a reliable mechanism to distinguish live objects from dead objects. Simply scanning memory cannot determine object validity. | GC scans every object independently. Objects are collected based on age alone. | Establish trusted entry points for reachability analysis. | Active thread stacks, static variables, JNI references, and active monitor locks serve as GC Roots. | What objects qualify as GC Roots? How does reachability analysis work? | Garbage Collection, Reachability Analysis |
| 13 | Reachability Analysis | Reachability Analysis is the process of traversing object references starting from GC Roots to identify live objects. Objects that cannot be reached are considered garbage candidates. Modern JVM garbage collectors rely on this algorithm. | Reference counting alone fails when cyclic references exist. Reachability analysis handles cyclic dependencies correctly. | Objects with references are always alive. Circular references prevent collection forever. | Determine object liveness accurately. | Two objects referencing each other but disconnected from GC Roots are still collected. | Why did JVM choose reachability analysis instead of reference counting? | GC Roots, Garbage Collection |
| 14 | Young Generation | Young Generation is the heap region optimized for short-lived objects. It consists of Eden Space and Survivor Spaces. Since most objects die young, this region experiences frequent but efficient garbage collection cycles. | Research revealed that the majority of objects become unreachable shortly after creation. | Young Generation simply means recently allocated memory. | Separate short-lived objects from long-lived objects for efficient collection. | Request DTOs, temporary Strings, and stream-processing objects. | Explain Minor GC and promotion mechanisms. | Eden Space, Survivor Space, Old Generation |
| 15 | Minor GC | Minor GC is the garbage collection process targeting the Young Generation. It focuses primarily on reclaiming memory from Eden and Survivor Spaces. Minor GC is typically fast because most objects are short-lived. | Frequent collection of temporary objects prevents heap growth and reduces pressure on Old Generation. | Minor GC is harmless and always invisible. | Reclaim short-lived objects efficiently. | A high-traffic API may trigger multiple Minor GCs every second. | What happens during a Minor GC? Why can frequent Minor GCs indicate allocation pressure? | Young Generation, Eden Space |
| 16 | Major GC | Major GC refers to garbage collection activity involving the Old Generation. Since Old Generation contains large numbers of long-lived objects, these operations are typically more expensive than Minor GCs. | Long-lived objects eventually accumulate and require cleanup. | Major GC and Full GC are always identical. | Manage memory occupied by long-lived objects. | Large caches, singleton services, and application-wide data structures. | Difference between Major GC and Full GC. | Old Generation, Full GC |
| 17 | Full GC | Full GC is a collection cycle that typically involves the entire heap, including Young Generation, Old Generation, and sometimes Metaspace. It is usually the most expensive garbage collection event. | When memory pressure becomes severe, broader cleanup is required. | Full GC means all memory is freed. | Reclaim memory from all major runtime regions. | Applications suffering memory leaks often exhibit frequent Full GC activity. | How do GC logs reveal Full GC problems? | Major GC, Metaspace |
| 18 | TLAB (Thread Local Allocation Buffer) | TLAB is a small memory region allocated to each thread inside Eden Space. Threads allocate most new objects from their private TLAB rather than competing for shared heap allocation. | Frequent synchronization during object allocation would create severe contention in multi-threaded applications. | TLAB is a separate memory region outside the heap. | Reduce allocation contention and improve scalability. | High-throughput web servers creating millions of objects concurrently. | Why is object allocation often faster than developers expect? | Heap, Eden Space, Threads |
| 19 | Safepoint | A Safepoint is a JVM state where all application threads are paused at known execution locations. At these points the JVM can safely perform operations such as garbage collection, deoptimization, thread dumps, and class redefinition. | Some JVM operations require a consistent view of application state. | JVM can pause threads at any instruction. | Provide safe synchronization points for runtime management. | Generating a heap dump requires reaching a safepoint. | Why do long-running loops sometimes delay GC? | Stop-The-World, Garbage Collection |
| 20 | Stop-The-World (STW) | Stop-The-World is an event where all application threads are paused while JVM performs internal operations. During this pause, application logic temporarily stops executing. | 21 | Escape Analysis | Escape Analysis is a JIT compiler optimization technique used to determine whether an object created inside a method can be accessed outside that method. The object may never need to be allocated on the heap at all. | Heap allocation and garbage collection are expensive compared to local variable operations. If JVM can prove an object is local to a method, it can avoid unnecessary heap allocation. | Every object created with `new` must be stored in heap memory. Escape Analysis is a security feature. | Enable advanced runtime optimizations that reduce memory allocation overhead and improve performance. | Temporary objects created inside frequently executed methods may never reach heap memory in optimized JVM execution. | What is object escape? | 22 | Scalar Replacement | Scalar Replacement is an optimization performed after Escape Analysis. | 23 | Lock Elimination | Lock Elimination occurs when the JVM determines that synchronization is unnecessary because a locked object is visible only to a single thread. | 24 | Compressed Oops | Compressed Oops (Ordinary Object Pointers) is a memory optimization technique where JVM stores object references using compressed representations rather than full 64-bit pointers.
