| 1 | Design Pattern | A Design Pattern is a proven, reusable solution to a recurring software design problem. | 2 | Pattern Language | Pattern Language is a collection of related design patterns that work together to solve larger architectural problems. | Individual patterns rarely solve complex systems alone. | Pattern Language is a programming language. | Enable systematic software design. | Enterprise application architecture. | How does Pattern Language differ from an individual Design Pattern? | Design Pattern, Architecture |

| 4 | Creational Patterns | Creational Patterns focus on object creation mechanisms and abstract the instantiation process. | Direct object creation often introduces tight coupling. | Creational Patterns only improve performance. | Increase flexibility in object creation. | Factory Method, Builder, Singleton. | Why separate object creation from object usage? | Factory, Builder |
| 5 | Structural Patterns | Structural Patterns focus on composing classes and objects into larger structures while keeping them flexible and maintainable. | Complex systems require efficient relationships between objects. | Structural Patterns modify business logic. | Improve system organization. | Adapter, Decorator, Proxy. | How do Structural Patterns improve maintainability? | Adapter, Composite |

| 7 | SOLID Principles | SOLID is a set of five object-oriented design principles that promote maintainable, scalable, and loosely coupled software. | Large codebases become difficult to maintain without design discipline. | SOLID is a design pattern. | Improve software quality and flexibility. | Spring Framework and enterprise applications. | Why are SOLID principles considered the foundation of good OO design? | OOP, Design Principles |
| 8 | Single Responsibility Principle (SRP) | A class should have only one reason to change, meaning it should have a single responsibility. | Classes often become difficult to maintain when they handle multiple concerns. | A class should contain only one method. | Improve maintainability and testability. | Service classes focused on a single business capability. | How can violating SRP increase maintenance costs? | SOLID, Cohesion |

| 11 | Interface Segregation Principle (ISP) | Clients should not be forced to depend on methods they do not use. | 12 | Dependency Inversion Principle (DIP) | High-level modules should depend on abstractions rather than concrete implementations. | Tight coupling reduces flexibility and testability. | DIP means using dependency injection only. | Promote loose coupling. | Spring IoC Container. | How does DIP support maintainable architectures? | Dependency Injection, Abstraction |
| 13 | Composition Over Inheritance | Favor composing objects together rather than extending classes through inheritance. | Deep inheritance hierarchies become rigid and difficult to maintain. | Inheritance should never be used. | Increase flexibility and reuse. | Strategy Pattern and Decorator Pattern. | Why is composition often more flexible than inheritance? | Strategy, Decorator |
| 14 | Coupling | Coupling measures the degree of dependency between software components. | 15 | Cohesion | Cohesion measures how closely related the responsibilities within a module are. | 16 | Abstraction | Abstraction focuses on exposing essential behavior while hiding implementation details. | Complex implementations should not burden consumers. | Abstraction means hiding all details. | Simplify system interaction. | Interfaces and abstract classes. | How does abstraction improve flexibility? | Interfaces, DIP |
| 17 | Encapsulation | Encapsulation bundles data and behavior together while controlling access through defined interfaces. | Unrestricted access leads to inconsistent object state. | Encapsulation means making everything private. | Protect object integrity. | Java Beans and domain models. | How does encapsulation support maintainability? | OOP, Information Hiding |
| 18 | Polymorphism | Polymorphism allows different objects to be treated through a common interface while exhibiting different behavior. | Flexible behavior should not require conditional logic everywhere. | Polymorphism is limited to inheritance. | Improve extensibility. | Strategy Pattern and Spring Beans. | Why is polymorphism a key enabler of OCP? | Interfaces, Inheritance |
| 19 | Design Smell | A Design Smell is a symptom indicating potential design problems that may reduce maintainability or scalability. | Poor design decisions accumulate over time. | A Design Smell is always a bug. | Identify areas requiring improvement. | God Classes and excessive coupling. | Why should Design Smells be addressed early? | Refactoring, Anti-Pattern |
| 20 | Refactoring | Refactoring is the process of improving internal code structure without changing external behavior. | Software design degrades as systems evolve. | Refactoring adds new functionality. | Improve maintainability and readability. | Continuous improvement in enterprise projects. | Why is refactoring considered an ongoing activity? | Design Smell, SOLID |
| 21 | Singleton Pattern | Singleton Pattern ensures that only one instance of a class exists throughout the application lifecycle and provides a global access point to that instance. | Certain resources should be shared and controlled centrally. | Singleton means using static methods only. | Prevent multiple instances of critical resources. | Configuration managers, logging frameworks, caches. | What problem does Singleton solve that static classes cannot? | Creational Pattern, Global State |

| 26 | Enum Singleton | Enum Singleton uses a Java enum with a single constant to implement Singleton behavior safely and concisely. | Reflection and serialization can break traditional Singletons. | Enum Singleton is just syntactic sugar. | Provide the safest Singleton implementation. | Configuration services and utility managers. | Why is Enum Singleton considered the preferred implementation? | Enum, Serialization |

| 33 | Builder Participants | Builder Pattern consists of Builder, Concrete Builder, Director, and Product participants. | Construction logic should be separated from object representation. | Builder only requires a Builder class. | Organize complex object creation. | Report generation and document creation. | What responsibility does the Director have? | Builder Pattern, Product |
| 34 | Fluent Builder | Fluent Builder uses method chaining to provide a readable and expressive object construction API. | Complex object creation should remain intuitive. | Fluent APIs automatically imply Builder Pattern. | Improve code readability. | Lombok @Builder and Stream API. | Why are fluent APIs popular in modern Java frameworks? | Builder Pattern, Method Chaining |
| 35 | Immutable Builder | Immutable Builder creates immutable objects by collecting state during construction and exposing only read-only fields in the final object. | Immutable objects improve thread safety and reliability. | Builder and immutability are unrelated. | Produce safe immutable objects. | Domain models and configuration classes. | Why are immutable objects often preferred in enterprise systems? | Builder Pattern, Immutable Objects |

| 43 | Dependency Injection | Dependency Injection supplies required dependencies from outside a class rather than creating them internally. | Tight coupling reduces flexibility and testability. | Dependency Injection requires Spring Framework. | Promote loose coupling. | Spring IoC Container. | Why is Dependency Injection considered a cornerstone of modern architecture? | DIP, IoC |
